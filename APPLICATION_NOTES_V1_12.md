# Application notes — v1.12 causal promotion evidence

Use this file when discussing rolling policy release, uncertainty, or Fraud Ops governance. It supersedes any interview wording that treats the cycle-3 **+20.2 pp** value-recall result as an online or causal queue gain.

PaySim is synthetic. Do not present these figures as Moniepoint production performance, prevented loss, analyst productivity, or a production SLA.

## Preferred governance bullet

Built a causal fraud-policy release audit on the full **6.36M-row PaySim** benchmark, combining rolling-origin retraining with seen-so-far analyst backlogs and family-controlled time-block uncertainty; a value-first candidate that appeared to add **20.2 pp** fraud-value recall in a retrospective whole-window queue added only **0.95 pp** under causal routing, so the governed decision remained `KEEP_INCUMBENT` across all 1/3/5/10-step dependence checks.

This is the stronger v1.12 bullet when the role values model governance, deployment evaluation, risk controls or experimentation discipline.

## Shorter version

Audited fraud-policy promotion under causal analyst capacity on **6.36M PaySim transactions**; replacing whole-window hindsight with a seen-so-far backlog reduced a candidate value-recall gain from **+20.2 pp to +0.95 pp**, and all pre-declared uncertainty checks retained the incumbent.

## Interview story

### 1. The governance rule was not the first thing I changed

The earlier release gate already had several controls:

- rolling time-separated train / calibration / policy / test stages;
- six pre-declared cycle/profile comparisons;
- family-wise error control;
- a +2 pp minimum primary gain;
- −2 pp non-inferiority guardrails;
- paired time-block bootstrap uncertainty;
- 1/3/5/10-step dependence sensitivity.

The missing issue was underneath the statistics: realised test queues were still generated by ranking the entire future window at once.

### 2. Whole-window top-k was label-safe but not causal

The retrospective policy did not use future fraud labels. However, an early transaction could lose a review slot because of a higher score that arrived many PaySim steps later.

That is appropriate for a completed-window ranking benchmark, but not for a claim about an online analyst queue.

v1.11 therefore introduced a seen-so-far backlog. v1.12 propagates that same contract into the rolling release gate.

### 3. I froze the promotion rule before changing the queue

I kept:

- **50 reviews / 10k**;
- official **5-step** block length;
- **2,000** bootstrap replicates;
- **family alpha 0.05** across six comparisons;
- **+2 pp** minimum primary gain;
- **−2 pp** guardrails;
- the original deterministic 5-step seed rule.

The intended methodological change is therefore the queue contract, not a favourable threshold or bootstrap setting.

### 4. The key result changed sharply

For cycle-3 value-first, the retrospective result was:

- incumbent alpha = **0.25**;
- candidate alpha = **1.0**;
- fraud-value-recall delta = **+20.20 pp**;
- family-adjusted lower bound = **+9.78 pp**.

But that comparison was based on whole-window top-k.

With a causal seen-so-far backlog:

- incumbent fraud-value recall = **39.46%**;
- candidate fraud-value recall = **40.41%**;
- delta = **+0.95 pp**;
- family-adjusted lower bound = **−0.81 pp**.

Candidate precision also moves from **87.32% to 84.51%**; its family-adjusted precision lower bound is **−7.47 pp** relative to the incumbent, which fails the −2 pp non-inferiority guardrail.

So the candidate is not close to promotion under the causal contract.

### 5. Dependence sensitivity also changes

In v1.10 retrospective evaluation, cycle-3 value-first was `DEPENDENCE_SENSITIVE`: block lengths 1/3/5 returned `KEEP_INCUMBENT`, but 10-step returned `PROMOTE`.

In v1.12 causal evaluation, **all 1/3/5/10-step settings return `KEEP_INCUMBENT`**. The result becomes `ROBUST_KEEP_INCUMBENT`.

Good phrasing:

> “The first uncertainty analysis made the candidate look borderline because the longest dependence block promoted it. After I corrected the queue to be causal, that apparent gain largely disappeared and every declared block length retained the incumbent. I treated that as evidence that the operational backtest contract mattered more than tuning the statistical gate.”

### 6. Keep the review-delay interpretation separate

Within cycle 3, the candidate causal backlog has mean review delay **2.68 PaySim steps** and p90 **8 steps**. Cycle 2 has longer backlog delays, around **8.5 steps mean** and **28–29 steps p90**.

These are dataset-step diagnostics, not hours, days, or a measured analyst SLA.

### 7. What I would test next

Each rolling test window currently starts with an empty evaluation backlog. A real release process must specify what happens to unresolved cases at a model refresh.

The next useful operational test is a **cross-refresh backlog hand-off**:

- keep the old score until review;
- rescore all pending cases with the new model;
- expire sufficiently old cases;
- or compare a controlled mixed hand-off.

That is a stronger next step than adding another classifier because it tests a real deployment decision created by the existing model lifecycle.

## Claims to avoid

Do not say:

- the old +20.2 pp was a production or online gain;
- v1.12 proves alpha=1.0 is bad in general;
- block bootstrap includes model-training uncertainty;
- PaySim steps correspond to hours or days;
- transaction amount equals prevented fraud loss;
- a production backlog should necessarily reset at each model refresh.

The safe conclusion is narrower: **under the declared PaySim rolling windows, exact analyst capacity, causal seen-so-far backlog, and frozen promotion rule, none of the six rolling candidates has sufficient evidence to replace the incumbent.**
